# esp32-c3-adblock

[English](README.md) · **Русский**

**DNS-блокировщик рекламы в стиле Pi-hole**, который работает на **ESP32-C3 за ~$2** — *без PSRAM*.

> 📰 О проекте писали [Tom's Hardware](https://www.tomshardware.com/networking/clever-hacker-fits-537-000-domains-in-a-tiny-usd5-esp32-ad-blocking-dongle-firmware-uses-only-around-50kb-of-ram-and-can-answer-blocked-lookups-in-10-milliseconds), [XDA Developers](https://www.xda-developers.com/this-tiny-esp32-powered-gadget-blocks-537000-domains-only-uses-50kb-of-ram/) и [Korben](https://korben.info/en/half-million-ad-blocking-domains-50kb-ram-esp32.html).

Главная идея, которую все упускают: блок-лист не нужно держать в оперативной памяти.
Домены хранятся как **отсортированные 40-битные хэши во флеше** и ищутся бинарным
поиском. Сотни тысяч доменов занимают ~1 МБ флеша и проверяются за ~10 мс, используя
**~50 КБ ОЗУ**.

```
запрос ──▶ извлечь домен ──▶ хэш FNV-1a (+ родительские суффиксы)
       ──▶ бинарный поиск по таблице хэшей во флеше
            ├─ найдено ──▶ ответить 0.0.0.0   (заглушка)
            └─ нет      ──▶ переслать на upstream-резолвер, вернуть ответ
```

## Почему это интересно

Большинство ESP32-«синкхолов» грузят блок-лист (строки доменов) в ОЗУ, поэтому требуют
PSRAM. Этот проект хранит **5-байтные (40-битные) хэши во флеше**:

| | строки в ОЗУ | хэши во флеше (этот проект) |
|---|---|---|
| Железо | ESP32 + PSRAM (~$8) | ESP32-C3 без PSRAM (~$2) |
| 141k доменов | ~2.5 МБ ОЗУ | **0.67 МБ флеша** |
| Занято ОЗУ | почти всё | **~50 КБ** |
| Поиск | сравнение строк | ~18 чтений флеша (~10 мс с учётом Wi-Fi) |
| Коллизии | — | 0 на 141k (1 на 537k) |

**Почему 40 бит?** Это оптимум для такого объёма флеша. Коллизии подчиняются правилу
дней рождения: на 141k доменов их ~0, на 537k — около 1 (то есть один «неудачный» домен
заблокируется лишний раз). 32 бита сэкономили бы 20% флеша, но дали бы ~7 коллизий на
250k; 64 бита потратили бы 3 лишних байта на домен ради проблемы, которой нет.

Тот же приём работает и на больших чипах — это не костыль для C3. На ESP32-S3 с 16 МБ
флеша эти хэши вмещают **~2.7 млн доменов** против ~466k для строк в 8 МБ PSRAM.

## Железо

- Любая плата **ESP32-C3** (проверено на C3 SuperMini), 4 МБ флеша, **PSRAM не нужна**
- Классический **ESP32** (DevKit / WROOM, 4 МБ) тоже собирается: `pio run -e esp32dev -t upload`
- Питание — от **стабильного USB** (зарядка телефона или USB-порт роутера). Дешёвые
  переходники USB-C→A могут «проседать» по питанию при передаче Wi-Fi.
- Переходник **USB-A → USB-C** позволяет воткнуть плату прямо в USB-порт роутера — без
  отдельного блока питания и корпуса.

### Корпус

Печатный корпус для C3 SuperMini: [`hardware/esp32-c3-supermini-enclosure.stl`](hardware/esp32-c3-supermini-enclosure.stl)

Замечания по печати:
- Поддержки не нужны; слои 0.2 мм, ~15% заполнения достаточно.
- **Не закрывайте антенну.** PCB-антенна C3 — зигзаг на короткой стороне напротив USB-C:
  не заливайте её пластиком и не кладите рядом металл, иначе пострадает RSSI.
- Оставьте вентиляцию: плата греется до ~45–55 °C.

## Сборка и прошивка (PlatformIO)

Одна прошивка по USB — дальше **и прошивку, и блок-лист можно обновлять** (см. ниже).

> ⚠️ Нужен **свежий PlatformIO** (встроенный в расширение VSCode или `pip install -U platformio`
> в venv). Старый `platformio` из apt (например, 4.3.4) не подходит и падает с
> `AttributeError: ... 'resultcallback'`.

```bash
# 1. скопировать шаблон секретов (в git не попадёт, остаётся локально) и отредактировать:
#    - WIFI_SSID / WIFI_PASS необязательны — можно оставить заглушки и настроить
#      Wi-Fi через портал на устройстве (см. ниже).
#    - WEB_USER / WEB_PASS / OTA_PASS обязательны: они закрывают изменяющие эндпоинты
#      дашборда (/ban, /addblock, /upload, /update, /setupdate, /forgetwifi) и сетевой OTA.
cp src/secrets.example.h src/secrets.h
#    затем отредактировать src/secrets.h

# 2. собрать таблицу хэшей блок-листа
#    (по умолчанию: Hagezi Pro + StevenBlack + Schakal RU AdList + AdGuard Russian,
#     ~266k доменов; российские сайты при этом работают)
python3 tools/build_blocklist.py data/blocklist.bin

# 3. прошить прошивку + файловую систему с блок-листом (единственная USB-прошивка)
pio run -t upload
pio run -t uploadfs

# 4. посмотреть загрузку, узнать IP / открыть дашборд
pio device monitor          # -> http://c3adblock.local
```

### Свои списки

`build_blocklist.py OUT.bin [SOURCE ...]` принимает любую смесь URL и локальных файлов
в форматах:

- **hosts-файлы** — `0.0.0.0 ads.example.com tracker.example.com` (берутся все домены строки)
- **простые списки доменов** — по одному домену на строку
- **правила AdGuard / Adblock** — `||ads.example.com^` блокирует, `@@||ok.example.com^`
  исключает домен (например, чтобы повторить allowlist из AdGuard Home)

Заблокированный домен блокирует и поддомены. Правила, которые DNS-хэш-лист выразить не
может (регэкспы, маски, `$`-модификаторы, косметические `##`-правила), пропускаются и
считаются. Правило `@@` снимает блокировку только с самого домена — оно не может вырезать
поддомен из заблокированного родителя. Если источник не скачался, сборка останавливается
(вместо тихой урезанной сборки) — ключ `--allow-missing` отключает это.

### Настройка Wi-Fi (без перепрошивки)

Если подключиться не удаётся (или `secrets.h` не задан), плата поднимает открытую точку
доступа **`C3-AdBlock-XXXX`** с captive-порталом — подключитесь с телефона, выберите сеть,
введите пароль. Чтобы позже сменить сеть: кнопка **Forget WiFi** в дашборде либо удержание
кнопки **BOOT** при включении — портал вернётся.

## Обновление по воздуху (больше не нужен USB для списка)

Дашборд на **http://c3adblock.local** умеет всё:

- **Блок-лист** — загрузите свежий `blocklist.bin` в *Blocklist → Upload* или укажите URL
  в *Remote auto-update*: плата сама скачивает готовый `blocklist.bin` по расписанию.
  Свежий список по умолчанию пересобирается **каждый день** через GitHub Actions и
  публикуется по постоянному адресу — вставьте ссылку один раз, и устройство остаётся
  актуальным само:
  `https://github.com/hybhyyb/esp32-c3-adblock/releases/download/blocklist/blocklist.bin`
- **Прошивка** — загрузите `.pio/build/c3/firmware.bin` в *Firmware → OTA update* (нужна
  таблица разделов с двумя app-слотами; при дефолтной single-app прошивка заливается по USB).
  Либо по Wi-Fi из CLI:
  ```bash
  pio run -t upload --upload-port c3adblock.local --upload-protocol espota
  ```

**Компромисс 4 МБ флеша:** в репозитории используется **single-app** `partitions.csv` —
без сетевого OTA прошивки (прошивка по USB), зато для списков освобождается **2.63 МБ**
(**до ~525k доменов**) и остаётся место, чтобы ежедневное авто-обновление писало новый
список рядом с рабочим. Если важнее сетевой OTA прошивки — переключитесь на dual-OTA
таблицу: два app-слота оставляют ~1.3 МБ под список (**до ~250k доменов**).

## Безопасность

Просмотр дашборда (`/`, `/stats.json`) открыт, но каждый изменяющий эндпоинт требует
**HTTP Basic Auth** (`WEB_USER`/`WEB_PASS` из `secrets.h`):

- `/ban`, `/addblock`, `/unblock`, `/forgetwifi`
- `/upload`, `/update` (блок-лист и OTA прошивки)
- `/setupdate`, `/fetchnow`

Сетевой OTA (`ArduinoOTA`) требует `OTA_PASS` из того же файла.

Без этого любой в LAN мог перепрошить устройство произвольной прошивкой или переписать
блок-лист без единого пароля — а плата стоит на пути каждого DNS-запроса вашей сети.
Имена пользовательских доменов экранируются перед отрисовкой в дашборде (закрыт
stored-XSS).

**Basic Auth — это контроль границы доверия LAN, а не шифрование.** Всё по обычному HTTP
на :80 — у чипа нет ресурсов на TLS-сервер. Учётные данные идут base64 (не шифруются) в
каждом запросе; кто уже может слушать ваш LAN-трафик, прочитает их. Это защита от
типичного случая — «другой устройство в сети без пароля» или CSRF из браузера, — а не от
атакующего на пути трафика.

**CSRF через кэшированный Basic Auth:** браузеры автоматически прикладывают сохранённые
Basic-креды к *любому* запросу на уже аутентифицированный origin, в т.ч. инициированному
чужой страницей (`<img src="http://c3adblock.local/forgetwifi">`). Поэтому все изменяющие
эндпоинты дополнительно требуют заголовок `X-Requested-With: c3-adblock`, который простая
`<img>`/CSRF-форма приложить не может (только same-origin `fetch()` — как и делает JS
дашборда).

**Учётные данные по умолчанию:** пока в `secrets.h` стоят заглушки
`CHANGE_ME_WEB_PASSWORD` / `CHANGE_ME_OTA_PASSWORD`, устройство запускается с публично
известным паролем. Прошивка пишет предупреждение в serial и показывает баннер в дашборде,
но всё равно загрузится — задайте реальные значения до использования в недоверенной сети.

Точка доступа портала настройки Wi-Fi (`C3-AdBlock-XXXX`) открыта (без шифрования) по
замыслу: к ней нужно подключаться, ещё не зная пароля. Вводимый пароль Wi-Fi защищён лишь
настолько, насколько безопасен этот короткий локальный радиоканал.

## Как использовать

Укажите DNS-сервер устройствам на IP платы — или добавьте плату **вторичным резолвером**
за вашим основным DNS. Проверка:

```bash
dig @<c3-ip> doubleclick.net   # -> 0.0.0.0  (заблокировано)
dig @<c3-ip> github.com        # -> реальный IP  (переслано)
```

## Почему плата, а не фильтры роутера?

В роутерах (Keenetic, Asus, TP-Link и др.) уже есть DNS-фильтрация — профили
Яндекс.DNS/AdGuard, списки dnsmasq. Для большинства это правильный ответ:
бесплатно, ничего покупать и обслуживать не надо. Плата выигрывает там, где
роутер обычно не может:

- **RU-покрытие и свежесть под вашим контролем.** Вендорские профили — то,
  что решил поставить вендор; RU-рекламные сети (Яндекс.Директ, AdFox,
  VK Ads, MyTarget) часто сидят на доменах, которые роутер не блокирует. Здесь
  список — ваш собственный микс (Hagezi Pro + StevenBlack + Schakal RU AdList
  + AdGuard Russian, ~266k), пересобираемый каждый день GitHub Actions и
  подтягиваемый автоматически.
- **Обновления не зависят от вендора.** Встроенный фильтр роутера обновляется
  по графику производителя (или никак); плата обновляет сама себя ежедневно,
  без участия прошивки.
- **Точечный allowlist и баны.** Разблокируйте ровно `youtube.com` (переживает
  любую замену списка) или забаньте целого клиента — по каждому устройству,
  из дашборда. Роутерные фильтры обычно «всё или ничего» по профилю.
- **Логи и счётчики.** Живой журнал DNS-запросов, счётчики блокировок по
  клиентам и дням — роутер для DNS-фильтра этого не показывает.
- **Роутер не трогаем.** Это отдельная коробка на DNS-пути: никакого риска для
  прошивки роутера, нет зависимости от того, будет ли вендор поддерживать
  фичу, и работает даже после смены маршрутизатора.

**Когда плата НЕ лучше:** если нужна максимально простая схема и подходит
встроенный фильтр роутера — оставьте его: лишнее устройство — это лишняя точка
питания и отказа. Ни тот, ни другой подход не лечит first-party подмену в
контенте (виджеты внутри `mail.ru` и т.п.) — это решается только расширением
в браузере / uBO, DNS-уровень на это не влияет. По скорости оба — на уровне
DNS (единицы мс); преимущество платы — контроль, свежесть списков и
RU-покрытие, а не сырая скорость.

## Подводные камни (проверено на практике)

- **ModemManager** (по умолчанию в Fedora/Ubuntu) хватает `/dev/ttyACM0` и дёргает
  DTR/RTS — это **сбрасывает C3** и блокирует serial. Лечится:
  ```bash
  sudo systemctl stop ModemManager
  echo 'ATTRS{idVendor}=="303a", ENV{ID_MM_DEVICE_IGNORE}="1"' | sudo tee /etc/udev/rules.d/99-esp-no-modemmanager.rules
  sudo udevadm control --reload-rules && sudo udevadm trigger
  ```
- Консоль USB-Serial-JTAG у C3 может «съедать» ранний вывод загрузки, пока хост не
  подключился (`while(!Serial)` помогает).
- DNS-клиенты добавляют запись **EDNS OPT**; ответ-блокировка должен содержать только
  question + answer (ANCOUNT=1, NSCOUNT=ARCOUNT=0), иначе он считается испорченным.
